## Сервис профилей пользователей

### Цели и функциональность

- Хранение чувствительных данных профиля пользователя (ФИО, телефон).
- CRUD-операции по профилю для самого пользователя.
- Просмотр профилей в админке только для пользователей с соответствующими правами (роль `admin`).
- Агрегированный просмотр пользовательской активности: закладки, отзывы и рейтинги (через существующий UGC-сервис).

### Архитектура и компоненты

- **FastAPI** – HTTP API, DI через `Depends`, разделение по роутерам:
  - `src/api/v1/profile.py` – эндпоинты профилей.
- **PostgreSQL + SQLAlchemy** – хранение профилей:
  - `src/models/profile.py` – модель `UserProfile` с полями:
    - `id` (UUID, PK),
    - `user_id` (UUID, FK-ссылка на пользователя, уникальный),
    - `full_name` (ФИО),
    - `phone` (телефон, уникальный, индекс),
    - `created_at`, `updated_at`.
  - `src/db/repositories/user_profile_repository.py` – репозиторий `UserProfileRepository`:
    - методы `get_by_id`, `get_by_user_id`, `get_by_phone`,
    - пагинированный `list_profiles`,
    - `create`, `update`, `delete`.
- **MongoDB + UGCService** – уже существующие закладки/лайки/рецензии:
  - `src/services/ugc.py` – используется как зависимость для `ProfileService`.
- **Сервисный слой профиля**:
  - `src/services/profile.py` – `ProfileService` инкапсулирует бизнес-логику:
    - работа с репозиторием профилей,
    - агрегация UGC (закладки, отзывы) по `user_id`.
- **Pydantic-схемы**:
  - `src/api/v1/scheme/profile_scheme.py`:
    - `UserProfileCreate`, `UserProfileUpdate`, `UserProfileOut`,
    - `UserProfileWithUGC` – профиль + закладки и отзывы.

### Эндпоинты и права доступа

- `GET /api/v1/profile/me`
  - Требует аутентификацию (`get_current_user`).
  - Возвращает профиль текущего пользователя + его закладки и отзывы.
- `POST /api/v1/profile/me`
  - Создание собственного профиля по ФИО и телефону.
  - При повторном создании – `409 CONFLICT`.
- `PATCH /api/v1/profile/me`
  - Частичное обновление ФИО и/или телефона.
  - При отсутствии полей – `400 BAD REQUEST`.
- `DELETE /api/v1/profile/me`
  - Удаление собственного профиля (`204 NO CONTENT`).
- `GET /api/v1/profile/`
  - Доступ только для роли `admin` (`check_role_permission('admin')`).
  - Пагинация через `PaginationParams` + фильтры `phone`, `full_name`.
- `GET /api/v1/profile/{user_id}`
  - Доступ только для роли `admin`.
  - Возвращает профиль пользователя + его UGC (закладки, отзывы).

### Почему выбраны такие технологии

- **PostgreSQL + SQLAlchemy**:
  - Реляционная модель подходит для чувствительных данных с жёсткими ограничениями (уникальность телефона, один профиль на пользователя).
  - SQLAlchemy уже используется в проекте, что соответствует принципу DRY и упрощает сопровождение.
- **MongoDB / UGC**:
  - UGC-данные (закладки, лайки, рецензии) уже реализованы на MongoDB и хорошо подходят для больших объёмов непредсказуемо растущих данных.
  - Повторное использование существующего `UGCService` снижает сложность и риск.
- **FastAPI**:
  - Уже базовый фреймворк проекта, даёт быстрый отклик, автоматическую валидацию и документацию.
  - DI через `Depends` позволяет чётко разделить ответственность и реализовать SOLID.

### Соответствие принципам SOLID, DRY, KISS

- **S (Single Responsibility)**:
  - `UserProfile` отвечает только за структуру данных профиля.
  - `UserProfileRepository` – за доступ к данным профиля в БД.
  - `ProfileService` – за бизнес-логику профиля и агрегацию UGC.
  - Роутер `profile` – только за HTTP-слой и коды ответов.
- **O (Open/Closed)**:
  - Логику легко расширить (например, добавить поле даты рождения или адрес) без изменения клиентского кода API.
- **L (Liskov)**:
  - Не используются наследования, где это могло бы нарушаться; типы и интерфейсы соблюдаются через явные зависимости.
- **I (Interface Segregation)**:
  - Репозиторий и сервис предоставляют узкоспециализированные методы, которые нужны конкретному слою.
- **D (Dependency Inversion)**:
  - Контроллеры зависят от абстрактного сервиса через DI (`ProfileService`), а сервис – от репозитория и `UGCService`, передаваемых извне.

- **DRY**:
  - Используются существующие механизмы:
    - авторизация (`get_current_user`, `check_role_permission`),
    - репозиторийный паттерн,
    - UGC-сервис для отзывов/рейтингования.
  - Общие структуры пагинации (`PaginationParams`) переиспользуются.

- **KISS**:
  - Профиль – одна таблица без сложных связей.
  - Для просмотра активности по фильмам используется уже готовый UGC-сервис без дублирования логики.

### Нефункциональные требования

- **Время ответа < 300 мс**:
  - Профили хранятся в PostgreSQL с индексами по `user_id` и `phone` – быстрый поиск.
  - UGC-запросы оптимизированы на уровне Mongo (индексы по `user_id` и `created_at`), список ограничен по дате и сортировке.
- **Коды ошибок и обработка входных данных**:
  - Pydantic-схемы задают ограничения по длине и формату полей (`full_name`, `phone`).
  - Используются стандартизованные HTTP-коды:
    - `400` – невалидный ввод,
    - `401/403` – отсутствие прав или аутентификации,
    - `404` – профиль не найден,
    - `409` – конфликт уникальности (дубликат профиля/телефона).
- **Минимум 5xx**:
  - Ожидаемые сценарии (нет профиля, конфликт телефона, отсутствие прав) обработаны явно и не приводят к необработанным исключениям.
  - Логику ошибок (`ValueError`, `LookupError`) сервис переводит в понятные HTTP-ответы на уровне контроллеров.
